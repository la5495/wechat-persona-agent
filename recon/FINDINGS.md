## 二、发送调用链（4.1.15.9，全部实测定位）

```
[上层发送逻辑，待续]
   └→ 0x39F47F0   （63998 B —— protobuf 生成的请求构造器）
        └→ 0x39E9860  （CoCgiSendRequest 封装，2741 B，字符串证据 'kernel::foundation::CoCgiSendRequest'、'mm_cgi.h'）
             └→ 0x39EC560  （CoCgiSendRequest/318 实现，1295 B）
```

- 定位手法：`newsendmsg` 字符串 → RIP 相对 xref → 函数簇 → `.pdata` 函数边界 → call xref 逐级上溯 + 运行时 `[rsp]` 返回地址
- 周期命中（~100 秒）= 同一机器处理 `newsync`（消息同步轮询）—— 不是 bug

## 三、发送请求元素结构（发送瞬间实测）

`0x39EC560` 的 args[1] = 请求缓冲；缓冲 +0x40 处是指向**消息元素对象**的指针：

| 字段 | 位置 | 实测值 |
|---|---|---|
| 目标 wxid | 元素 +0x08 → 嵌套 string wrapper → +0x08 | `filehelper` |
| **正文** | 元素 +0x10 → 指针直指文本 | `WXTEST44444 返回点` |
| msgsource | 元素 +0x20 → 指针直指 XML | `<msgsource><alnode><fr>1</fr></alnode></msgsource>` |

同一次发送还拿到：
- `sending_filehelper_1790178549_61_1` —— clientMsgId（发送瞬间时间戳吻合）
- `wxid_你的wxid` —— 发送者（主人自己）
- `weixin.qq.com` / `default-longlink` —— 网络任务描述符（MARS 长连接）

## 七、09-24 凌晨的两条更正（重要）

1. **回溯链在 0x1851AA0 之上不可信**：ACCURATE 回溯给的 `0x492440/0x4912A0/0x74AE5CF`
   实测是 **mars/SMC 统计机器**（`smc_core.cc:mars::smc::SmcCore::ReportKVSample`、
   `szextshort.weixin.qq.com`，每秒触发几十次）—— 协程栈展开漂移了，**不是发送链**。
   可信的发送链止于：`0x1851AA0 → 0x18527A0 → 0x3973CE0 → 0x39F47F0 → 0x39E9860 → 0x39EC560`。
2. **第二次崩溃（0:01:13，0xc0000409 fail-fast）**：根因是人家自己的操作失误 ——
   `job_kill` 强杀上一个观察器后**同一秒又注入新 agent**，两个 agent 撞车，微信被带崩。
   **教训：观察器必须优雅卸载；kill 后要等 60 秒以上让 agent 自卸（实测：自卸后 CPU 增量 0.3s/20s，干净）。**
   此外：**钩热函数（每秒几十次）会让 unload 挂死** —— 热函数只可短暂观察，不可长挂。

## 八、「调用发送函数」实验设计（未执行，明日按此执行）

目标：在 frida 里调用 `0x39F47F0` 构造并发出**任意文本**消息。

1. **线程亲和**：0x39F47F0 跑在消息协程线程。调用它必须**在那个线程上** ——
   办法：钩一个在该线程上的函数（如 0x74AE5CF），在它的 onEnter 里执行调用（thread hijack within hook）
2. **参数克隆**：在真实发送的 onEnter 里，把 4 个参数指向的**对象图深拷贝**（深度 3-4、
   所有堆指针都跟进、新内存用 Memory.alloc 分配并重写指针），得到可复用的请求骨架
3. **改文本**：在克隆图里按第三节结构把正文指针换成新文本（+改长度字段）
4. **调用**：用 1 的办法在正确线程上调用，只发「文件传输助手」
5. **防护**：调用前跑 health.py；调用只做一次；一旦异常立即停手；每次实验间隔 ≥60s

风险等级：中高（构造错对象可能崩微信）。建议：**微信冷启动后、主人在场时做**。

## 九、09-24 上午的进展（实验一：正文改写）

### 复验的路径（全新会话，08:54 / 09:15 两次实测）

```
A0 = args[2]  (0x39EC560 的第三个参数)
A1 = *(A0 + 0x08)
A2 = *(A1 + 0x00)
N1(目标包装器) = *(A2 + 0x08) → *(N1 + 0x08) = 目标 wxid 字符串（"filehelper"）
N2(正文包装器) = *(A2 + 0x10) → *(N2 + 0x00) = 正文字符串
N2 布局：+0x00 数据指针 │ +0x08 = 0 │ +0x10 字节长度 │ +0x18 容量
```

### 两个实验，两个结果（都很关键）

| 实验 | 做法 | 微信 | 实际发出的正文 |
|---|---|---|---|
| **v2 改指针** | `N2+0x00 = frida 分配的缓冲`；改长度/容量 | ❌ 发完就退出（**无 APPCRASH 记录** = 微信自己报错退出） | ✅ **我们的文本**（`HOOKPATCH-OK1 钩子改文本` 09:06:11 入库） |
| **v3 原地覆写** | 往 `*(N2+0x00)`（微信自己的缓冲）**原地写**新内容 + 改长度；**指针/容量不动** | ✅ 存活 | ❌ 原文（`UITRIGGER 实验一原文` 09:15:36 入库） |

### 结论（两条合起来指明正解）

1. **v2 证实**：hook 完全能**控制发出去的内容**（消息真的带着我们的文本出门了）。
   崩的原因是**指针所有权**：把微信的字符串指针指向 frida 的缓冲后，微信稍后
   按其自身的分配器释放该指针 → **invalid free → 堆损坏**。（所以绝不能改数据指针）
2. **v3 证实**：在 `/318` 入口改**源对象**太晚了 —— 此时**序列化已完成**，
   正文早被复制进请求缓冲，改源对象不影响出网内容。（顺带证明"原地覆写"本身是安全的）
3. **正解方向**：把改动点**前移到序列化之前** —— 钩 `0x39E9860`（CoCgiSendRequest 封装）
   或 `0x39F47F0`（构造器），在那里原地覆写正文，让序列化时读到的是我们的文本。
